Overview

vecdex is a C++20 library for approximate nearest-neighbor (ANN) search: given a query vector, it returns the k stored vectors closest to it without comparing the query against all of them. It is built on HNSW (hierarchical navigable small world) graphs, with hand-written NEON and AVX2 distance kernels, a multithreaded build, crash-safe save and load, and Python bindings that read NumPy arrays in place.

The algorithm fits on a page of the paper; the work is in making it fast and measuring it fairly. A search is a chain of cache misses: every node it expands leads to about 21 unvisited vectors, scattered across 512 MB. I profiled before optimizing, and I benchmarked vecdex against hnswlib and FAISS on one machine, through one harness, with the same build parameters, and even with vecdex's own distance kernel plugged into hnswlib, so the remaining gap measures graph code alone.

How it works

Every vector is a node on layer 0; a random, exponentially thinning fraction also lives on layers 1, 2 and up, like the express lanes of a skip list. Vectors sit in one contiguous row-major buffer, and each node's layer-0 links are a fixed-size block in one flat array, so following a link never chases a per-node allocation. For each node it expands, a search filters the unvisited neighbors (an epoch-stamped visited array that resets in O(1)), prefetches all their vectors, then computes distances with the NEON kernel and updates two heaps in pooled scratch memory. A warm search allocates only the vector it returns.

Prefetch every neighbor before computing any distance

A sampling profile of the first working version put 96% of search time in the layer search and the distance kernel, and the kernel was mostly waiting on memory: each expanded node reads about 21 random 512-byte vectors, a cache miss apiece. Requesting all of them before the first distance lets the misses overlap. Against the version before it, that nearly halved the time per query (1.90×) and cut the build by 41%, without changing the storage format.

It also explains the gap to hnswlib: with vecdex's kernel, hnswlib runs at 9,190 QPS at ef = 64, almost exactly vecdex's speed before prefetching (9,074). On x86, where hnswlib's own prefetching is compiled in, the gap may be smaller; that was not measured.

One lock per node, and never two at once

A parallel build stores every vector first, then threads claim nodes from an atomic counter. Each node's links have their own mutex, a thread never holds two node locks, and a node becomes reachable only after its own links are written, so no thread can link to a half-built node. Searches take no locks: a compile-time policy keeps the locking code out of search() entirely. ThreadSanitizer finds no races, and a parallel build's recall matched the serial build in every run.

A durable save and a hostile load

The index is written to a temporary file, flushed with F_FULLFSYNC (on macOS plain fsync leaves data in the drive's cache), renamed over the old one, and then the directory is flushed: a power cut leaves the old index or the new one, never neither. Loading treats the file as hostile. Every count is checked against the file size before anything is allocated, then the XXH64 checksum, then the graph itself (ids in range, no self or duplicate links, consistent layers) before any link is followed. A libFuzzer run of 1.5 million inputs found nothing.

Limits

  • No deletes or updates. The index only grows.
  • No vector compression. Without product quantization (PQ), 1M × 128 floats take 512 MB of the 650 MB SIFT1M index.
  • Loading reads the whole file. The format's sections are not aligned, so the index cannot be mmap-ed.
  • No filtered search, such as metadata predicates applied during the graph walk.
  • One machine. Every result is from one Apple M4; on x86, where hnswlib's SIMD and prefetch paths are active, the comparison would differ.
