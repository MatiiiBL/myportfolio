Overview

Pulse is a small system-on-chip I wrote in SystemVerilog. A 5-stage pipelined RISC-V CPU (RV32IM: the base integer instructions plus multiply and divide) drives a neural processing unit (NPU): an 8 × 8 systolic array of INT8 multiply-accumulate cells with its own DMA engine. Bare-metal C firmware, built with clang, programs the NPU through memory-mapped registers. In cycle-accurate simulation of the RTL, quantized MNIST runs 115 times faster on the NPU than on the CPU alone, with bit-identical results. The design meets timing at 40 MHz on a Lattice ECP5 FPGA with a fully open-source flow: it is placed and routed, but has not yet run on a board.

The array is the easy part. The hard parts are keeping it fed and proving the chip right. A full tile needs a new operand for each of the eight rows and eight columns, 16 bytes, every cycle, so the memory system, not the multipliers, sets the throughput. And the RTL is checked against a C++ reference simulator written separately from the same spec, compared at every retired instruction on thousands of random programs, while the NPU is tested bit for bit against a Python model in six array and port configurations.

Interactive

The array, cycle by cycle

One NPU command at the timing of the RTL. The CPU writes the registers and START; the DMA loads each row of A and B into the operand buffers, one 16-byte block per cycle; then the operands enter the array skewed. Row i of A enters from the west and row j of B from the north, each one cycle behind its neighbor, so A[i][k] and B[j][k] meet in PE (i, j) at step k + i + j + 3. Every processing element (PE) multiplies its pair, adds the previous product to its own INT32 sum and passes both operands on. The sums never move (the array is output-stationary); write-back drains them to memory, one per cycle. The skew costs no delay registers: each row's feeder reads its operand buffer one step later than the row above.

How it works

Two implementations of one spec

The RTL and a C++ instruction-set simulator are written separately against one spec, which fixes the memory map, the bus timing and the NPU's exact arithmetic. Random programs run on both, and their commit logs (PC, instruction, register write, memory access) must match line for line, so a bug has to be made twice, in two languages, to go unnoticed. The tests were tested too: of 23 bugs injected into the NPU RTL, the suite caught 22, and the survivor writes a word that is always overwritten.

A memory port for the NPU

The data memory is four word-interleaved, true dual-port banks. The CPU uses one 32-bit port; the NPU's DMA reads or writes a 16-byte block per cycle on the other, so it never stalls the CPU, and banking costs no extra block RAM. That made MNIST on the NPU 1.9 times faster. A full tile still needs 16 new operand bytes per step, so the NPU also keeps what it loaded: A_KEEP and B_KEEP skip reloading an operand, and because the NPU tags each buffer with its address, stride, rows and K, a wrong hint costs time, never correctness.

Clock over CPI

Forwarding load data from block RAM put the RAM's clock-to-out, bank steering, alignment and an adder in one cycle. Loads now reach their consumers through the register file instead, one or two bubbles later. That costs 15% CPI on CoreMark and buys a 1.6 times faster clock: a net 1.39 times faster on CoreMark and 1.59 times on MNIST.

Limits

  • Not yet run on a physical board. The bitstream builds and meets timing at 40 MHz, and its firmware runs in simulation with the board's real UART logic.
  • A simple memory system. No caches and no external memory: a program and its data must fit in 64 KiB + 256 KiB. The MNIST demo runs 100 test images in hardware and reports accuracy over all 10,000 from the bit-exact Python model (98.07%).
  • The NPU runs one phase at a time. Loading, computing and writing back happen in sequence. Double-buffering the operand banks, half used at the maximum K of 1024, would overlap the next load with the current compute.
  • Past 40 MHz needs a decoupled fetch queue (the critical path runs from the instruction memory through decode to the stall) and a two-stage multiplier.
  • CoreMark runs 10 iterations to keep simulation short, so the score is not a valid submission under CoreMark's run rules.
