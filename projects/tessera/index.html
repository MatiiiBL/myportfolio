Overview

Tessera is a tensor compiler for Apple silicon that I wrote from scratch: about 28,000 lines of Python and 1,600 of C and Objective-C. It imports an ONNX model, rewrites and fuses its graph, lowers each fused group to a loop IR modeled on TVM's TensorIR, and schedules those loops with templates whose knobs an autotuner sets with a learned cost model. The output is C with hand-written NEON and SME microkernels for the CPU, or Metal Shading Language for the GPU, built on a stock Mac without Xcode.

The hard part is speed without wrong answers. Every schedule primitive rewrites the loops around a computation and must leave its result unchanged, or refuse. Every tuned configuration has to be faster inside the model, not only when timed alone. On an Apple M4 the GPU backend is the fastest system measured on all four benchmark models (ResNet-50, MobileNetV2, BERT-base and GPT-2), 1.13 to 1.56 times the best baseline, and every output agrees with ONNX Runtime to within 3e-6 of its largest magnitude.

Interactive

Scheduling one kernel

This is the kernel Tessera's documentation uses to show its generated C: a matrix product with a bias and a ReLU, fused into one group. The controls are the five knobs of the CPU matmul template on the portable C target. Changing one runs the template again. It splits the row and column loops into register tiles, moves the reduction inside them, accumulates each tile in a local buffer, inlines the ReLU into the tile's write-back and, in nm order, copies each strip of W into a contiguous buffer before the row tiles that use it.

On the M4's SME target the same template stops at the tiles and hands each one to a microkernel through tensorize, which first checks that the loop nest computes exactly what the microkernel's description says. Fusion decides how many such kernels a model needs. In a ResNet-50 bottleneck, each ReLU and the residual Add run inside the convolution before them, so their inputs never go through memory.

Autotuning

Every distinct fused group is a tuning task: 78 per target over the four models, with 3.1 million configurations in all on the CPU and 420 million on the GPU. An evolutionary search proposes candidates and a gradient-boosted cost model, written in NumPy and trained on features of the scheduled loop nests, ranks them. The 25,651 measurements are committed as logs. On a synthetic task with a known optimum, model-guided search finds better schedules than random search for the same number of measurements; on real tasks, where measurements are noisy, the difference is smaller.

Fusion and kernels

Fusion leaves 37 to 53% as many kernels and moves 23 to 43% fewer bytes. On the GPU it makes every model faster (1.02 to 1.19 times); on the CPU the difference is within the noise. One arena holds every intermediate tensor in 3.9 to 31 times less memory than separate buffers. On the shapes of the transformer layers, the SME GEMM is 1.16 to 1.47 times Accelerate's speed; at 2048³ the Metal GEMM is within 3% of MPS.

How it works

Schedules that can be checked

The loop IR separates what a block computes from the loops around it. A block declares its iteration domains and the regions it reads and writes, and schedule primitives (split, reorder, fuse, compute_at, cache_read, tensorize and the rest) rewrite only loops and bindings. Each primitive's legality check is therefore local, and it refuses with an error rather than miscompile. A Python interpreter runs any scheduled function, so every schedule can be compared with the unscheduled one: a randomized test applies up to ten random primitives to random computations, 300 times per run, and checks the result each time.

Microkernels by tensorization

The inner loops that matter are written by hand once per instruction set: an 8×12 register tile for NEON, and for SME a 32×32 block of the output held in the ZA array, with four fmopa outer products per step of the reduction and one entry into streaming mode per macro block. tensorize matches a loop nest against a microkernel's description, edge tiles included, so templates only decide tiling, order and parallelism. Without schedules the generated C is 28 to 417 times slower; without SME, 2.2 to 2.9 times slower on three of the four models.

Time what the model runs

The first tuning run made GPT-2 slower on the CPU, because kernels timed alone disagreed with the same kernels inside the model. The main cause was thread placement: macOS moved busy SME worker threads to the efficiency cores, and a spinning worker stayed there. Idle workers now sleep, iterations are claimed dynamically, and a worker woken on an efficiency core leaves the loop to the others. Kernels are timed with cold, pre-packed weights, as a model run reads them, and tuned configurations are validated inside the models before they are used; that pass found about a quarter of them slower in the model than the defaults.

Limits

  • Batch 1, float32, static shapes. There are no int8 or float16 kernels, and dynamic dimensions are fixed at compile time.
  • CPU convolutions trail PyTorch's. Measured kernel by kernel, Tessera beats PyTorch on the CPU on 4 of ResNet-50's 23 convolution shapes, although the whole model is faster (11.52 against 13.18 ms). Large square GEMMs and GPT-2's vocabulary projection are slower than Accelerate (0.71 and 0.66 times).
  • Thread placement on the CPU. macOS sometimes keeps one SME worker on an efficiency core for a whole process, which then runs on three threads: ResNet-50 takes about 15.5 ms instead of 12. No user-space fix is known.
  • Strided convolutions on Metal. Six of ResNet-50's seven are slow: 212 to 322 GFLOP/s, against a median of 1,374 over all its convolution shapes.
  • Tuning covers a small part of each search space, and the logs are specific to the M4 they were made on.
